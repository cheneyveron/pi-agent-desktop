# 主会话、记忆与工作台：从模型的局限出发

2026-11-01，第六稿（第五稿 + 六组实验的结果，实验在 `~/workspaces/experiments/2026-11-memory/`，每组一份 REPORT.md）。前四稿的问题：先照搬文章，后在 tracker 上叠层，再被中途意见牵着改，始终没有回答最核心的问题——**模型在每一次调用里只知道上下文里有什么，那么主会话每一轮的上下文由什么构成，什么放上下文、什么放记忆、什么两边都不放。** 这稿从这里开始。

## 1. 最终目标

一个持续知道你全部工作状态、替你记住学到的东西、在该做下一步时提醒你或替你做只读准备的系统。四个痛点（切换、follow-up、重复读仓库、记忆没用上）都是它的推论。

## 2. 模型的行为与局限，以及由此得出的规则

每条规则下面的设计都得服从它。

**L1. 每次调用无状态。** 模型知道的 = 训练 + 系统提示 + 上下文里的消息。没有别的。
→ 任何"它应该记得"的东西都必须在每一轮被放进上下文，或者它永远不知道。

**L2. 它不知道自己不知道什么。** 给它一个 `recall` 工具，它只在已经怀疑"这事以前讨论过"时才调；绝大多数时候它不怀疑，就不调。pi-hindsight、pi-memhana 的 recall 工具在你这里几乎没被调过，scipq 同理。
→ **记忆靠推送，不靠拉取。** 召回由控制面在固定时机执行并注入；工具只作补充。这是整份设计最重要的一条。

**L3. 长上下文的注意力不均匀。** 开头和结尾强，中间弱；无关内容稀释相关内容；每轮都要重读全部上下文，前缀稳定才有缓存。
→ 上下文要小、要稳、要有序：固定部分放前面不动，变化的部分放后面，推送的东西有预算，相关的放靠近当前消息处。

**L4. 它擅长的：**总结自己上下文里的东西、在给定候选里判相关、按模板出结构化输出。**不擅长的：**跨调用的一致性、对"是否记得"的校准、长程的承诺（它不会"记得"三天后去跟进）。
→ 交接由会话自己的模型做（东西在它上下文里）；判断（归线程、取舍）由主会话在被推送了候选之后做；跟进全部外化成条件，由代码检查。

**L5. 压缩会丢细节。** 压缩摘要只保留摘要提示要求的东西。
→ 压缩之前先交接。交接是防丢的最后一道，不只是空闲时的例行。

**L6. 它用训练时见过的工具。** grep / find / read 会用，新名字的工具不会用。
→ 结构塞进它已经在调的工具后面，不新开工具。

**L7. 记忆服务本身也是模型做的。** memhana 的写入是 LLM 抽取说法，召回是 embedding + reranker + PageRank；它的评测语料是聊天和小说；延迟 2–5 秒；过期只认用户改口。
→ 召回结果是参考，不是真相。状态在文件里，文档在 kb 里，memhana 只负责"学到过的事实和决定"。设计不能依赖 memhana 与别的层同步得好。

## 3. 结论

一个**主会话**，但它不是"一个很长的对话"，而是**一个持久的外部状态 + 每轮按策略重建的短上下文**。工作会话在空闲 5 分钟或压缩前做**交接**；交接机械地写 tracker 的状态部分和 memhana，再作为事件推给主会话。主会话每轮的上下文由控制面从状态重建（§4）。展示靠工作台页面。pi 继续做 loop；pi-agent-desktop 的服务端变成控制面。

## 4. 主会话的上下文（核心）

### 4.1 每一轮上下文由什么构成

按 L3 分层，从前到后：

| 层 | 内容 | 大小 | 变化频率 | 来源 |
|---|---|---|---|---|
| A 固定 | 角色、规则、工具说明 | ~2k 字 | 几乎不变 | 系统提示，缓存 |
| B 全局板 | 每个**近期**线程一行：id、状态、最后活动日期、`Status` 首句、下一步首项、等待中的条件。近期 = 30 天内有活动，或有未到的部署日，或被本次事件提到 | ≤ 40 行 × 150 字 ≤ 6k | 每次交接后变一两行 | 控制面从 tracker 文件生成 |
| C 滚动窗口 | 你和主会话最近 N 轮对话原文（N=5 够：你一天问它一两次） | ≤ 3k | 你说话时变 | 会话文件，按策略筛 |
| D 本次事件 | 一份交接 / 一个检查器结果 / 你的一句话 / 每日 tick 的清单 | 1–3k | 每轮 | 控制面推送 |
| E 事件相关 | 涉及线程的完整 tracker（状态部分 + 快照部分）；该线程最近 3 条交接；记忆召回（§6，预算 3k 字） | ≤ 8k | 每轮 | 控制面推送 |

每轮总量 15–20k 字。没有"主会话自己处理过的历史事件"这一层：那些事件的后果已经写进 tracker 和记忆，再留在上下文里只是稀释（L3）。实验 E 用 92 个真实 tracker 回放时，不过滤的板是 8.6k 字、37 轮里 5 轮超过 20k；过滤到近期线程是把预算拿回来的唯一办法。板上没有最后活动日期时，"哪些线程一周没动"答不出来。

### 4.2 怎么做到"每轮重建"

pi 会话文件是只追加的，但 pi 有 `context` 钩子：扩展可以在每次调用 provider 前替换模型看到的消息列表（pi-memhana 已经用它只保留最新一份注入）。主会话的扩展就用它：

- 文件里保留全部历史（审计、回放）。
- 模型看到的 = A + B + C + D + E。C 只取 `role: user` 来自你的轮次和紧随的回复；控制面投递的事件轮次（交接、检查器）一旦处理完就不再进入 C。
- B 和 E 每轮现算现注入，不依赖上一轮注入过什么。
- 因此主会话**不需要压缩**：模型看到的从来不超过预算。文件再长也无所谓。

### 4.3 什么放上下文，什么放 memhana，什么都不放

| 东西 | 放哪 | 为什么 |
|---|---|---|
| 所有活动线程的存在和一行状态 | 上下文（B），每轮 | L2：不在上下文里它就不知道有这个线程，就归不对、合不了 |
| 当前事件涉及线程的全文 | 上下文（E），按事件 | 判断需要细节，但只要相关线程的 |
| 线程的历史交接 | 文件 `Log` 里；最近 3 条进 E；更早的靠 memhana 召回 | 全放稀释；全不放丢背景 |
| 事实、决定与原因、你的纠正、人和系统 | memhana；按事件内容召回进 E | 数量无界，不能常驻；按需推送是唯一可行方式 |
| 主会话处理过的事件 | 不放。后果在文件和 memhana 里 | L3 |
| 你和它的近期对话 | 上下文（C），N 轮 | 对话连续性；超过 N 轮的，重要的已被它写成记录 |
| 已关闭线程 | 不在 B；按事件 id 命中时整份进 E | 关了就不占板 |
| kb 文章 | 不常驻；控制面按线程 / 仓库标签命中时把摘要 + 路径放进 E，模型用 `read` 取全文 | 长文整篇进上下文太贵；靠标签推送比靠它想起来可靠（L2） |

### 4.4 主会话做什么、不做什么

- 做：把交接归到线程（或建线程、或判定不值得跟）；改 `Progress` 里的 `run:` / `on:`；条件触发后决定派只读工作会话还是标 `needs-me`；决定哪些 `learned` 值得写记忆、哪些是噪音；发现两个线程是一件事就合并；回答你"X 怎么样了""这周我欠什么"。实验 E 里两个模型 24 次归线程零次归错已有线程；分歧只在无编号会话该不该建线程。
- 检查器事件的响应有固定动作集：必须更新 `Progress` 那一行，条件意味着要你动手就标 `needs-me`，只读的后续才 `dispatch`。不约束时两个模型风格各异。
- 不做：中介你和工作会话；任何写操作；替你发消息；主动起长对话。
- 工具：`threads`、`memory`（recall / remember / forget / feedback）、`sessions`（读交接、带线程上下文起工作会话、steer）、`waits`、`notify`。没有 bash、没有文件工具。
- 模型：实验 E 里 `gemini-3.8-flash` 与 `gpt-6-luna` 归线程、改 Progress、答问持平；flash 更多标 `needs-me`（11 比 5），但写记忆少（7 比 17），提示要强制每份交接至少一条 `remember`。先用 flash。

## 5. 工作会话的上下文

- **启动推送**（控制面，`before_agent_start`）：关联的 tracker（若有）→ 按"首条消息 + cwd 仓库"的记忆召回（§6；预算 **6k** 字，带锚点的说法附路径，模型直接 `read`，少 `grep`）。全部推送，不等它来问（L2）。预算定 6k 不是 3k：实验 C2 里两种召回从 3k 到 6k 完备率都 +0.13，比换系统的差别大。
- **工作中再推送的门**：每条用户消息都召回会加 2–5 秒延迟和噪音。折中：控制面用正则看新消息里是否出现上下文里还没有的 ticket id / 客户名 / 人名 / 仓库名；出现才召回一次，预算 1k 字，去重已注入的。没出现不召回。`recall` 工具保留，但不指望。
- **交接时机**：空闲 5 分钟且有新工具活动；**压缩开始前**（L5，接 `compaction_start`）；会话被关闭前。每次增量。
- **交接由会话自己的模型做**：东西在它上下文里（L4），缓存命中，一轮便宜；小模型读 600 条消息会丢。
- 交接提示明确要字段，尤其"用户说过的话和纠正"和"下次做这类事你希望一开始就知道什么"——模型默认只报自己做了什么（L4）。实验 B 证实：24 个真实会话上两种模型零幻觉、`stands` / `learned` 可靠，弱的正是 `user_said`、`open` 和 `on:`；交接文本对事实的覆盖率 95%（实验 C2 的 write-loss 4.6%），即交接这一步不丢东西，丢在召回。

## 6. 记忆层：实验之后的定位

### 6.1 实验说了什么

实验 C2（25 个未入库的真实会话的首条消息作 query，24 份交接入库，LLM 判分，`memhana-eval-2/REPORT.md`）：

| 条件 | 完备率 | 延迟 | 字数 |
|---|---|---|---|
| memhana，仓库过滤，中文 context，3k | 0.305 | 18 s（首次） | 2.9k |
| memhana，仓库过滤，6k | 0.443 | 1.3 s | 5.9k |
| BM25 直接搜交接文件，3k | 0.310 | 0.01 s | 2.8k |
| BM25，6k | 0.443 | 0.01 s | 5.6k |
| memhana `items` 自己紧凑渲染，3k | **0.425** | 1.3 s | 2.2k |
| BM25 前置 + memhana 补足，3k | 0.310 | 1.0 s | 3.0k |

- 写入不丢：交接全文覆盖 95% 的事实。丢在召回：预算 3k 时丢 65%，6k 时丢 51%。预算比系统重要。
- 同预算下 memhana 和 BM25 总分打平，但赢在不同题上：memhana 赢跨会话链（provisioning 三个会话串起来、PR 合并检查），BM25 在这些题上是 0；BM25 赢细节题（commit、API 路径、字段名原文），memhana 的说法把这些压掉了。15 题里 memhana 独有价值的是 2–3 题。
- 修订有效：写一条相反的用户记录后，旧说法标 superseded、新说法 current。BM25 做不到。
- kb 混进同一个 bank：上下文 ×4、噪音 ×5、完备率几乎不变；只有 kb 的 bank 最差（0.131）。
- 运营：rdsec 提供 embedding（`text-embedding-3-small`），不需要本地模型；写入异步，每会话约 0.22 USD；中文 `context` 比 `items` 多 48% 字且首次 18 s；仓库过滤使召回快 14 倍。

### 6.2 定位

**记忆 = 交接文件本身 + 一层检索。** 交接 JSON 按会话存在控制面（`~/.pi/agent/closeouts/<session>.json`，也是 tracker `Log` 的来源）。这份文件就是真相；检索只是从中选出放进上下文的那 6k 字。

两段落地：

1. **第一段：BM25。** 控制面内置，对当前仓库的交接文件做 BM25，取 6k 字，`learned` / `user_said` 行优先。零延迟、零成本、无服务，完备率 0.44，和 memhana 6k 持平。先上这个，让交接和启动推送跑起来。
2. **第二段：memhana 作为第二路。** 同一次启动，再向本地 memhana 要一份 `items`（仓库过滤、紧凑渲染、2–3k），与 BM25 块并列注入，各自标明来源。它补的是 BM25 补不了的两样：跨会话链、修订（旧结论被你改口后不再以 current 面目出现）。是否值得这 1–2 秒和每会话 0.22 USD，用真实会话 A/B 两周决定：统计模型在启动后是否还重搜、是否被旧结论误导。

memhana 不再承担"记一切"的角色；它承担"把多个会话的结论连成链并跟踪谁被推翻"。设计的其余部分不依赖它。

### 6.3 memhana 要改的（按实验）

- 服务端提供紧凑的 `items` 渲染（或控制面自己渲染，已验证）；中文 `context` 不用于注入。
- 记录 / 来源的 stale 允许外部打标（git blob 变了），召回带出。
- `write.sparse` 对交接记录关掉：交接每行都值得成说法（实验 C 里 attached 0.58）。
- 费用剖析一次：每会话 0.22 USD 可接受，但记录数随 `user_said` 行数线性增长。
- 不需要改引擎。Hindsight 对比（`hindsight-vs-memhana/REPORT.md`）：前提边、修订、本地 SQLite 都是 memhana 占优，Hindsight 的矛盾事实并存、召回秒级，不换。

### 6.4 kb：第一版不用

实验证据：kb 文章混进记忆只添噪音，单独用最差；而交接文件本身覆盖 95% 的会话事实。所以第一版**不把 kb 纳入设计**：不同步、不推送、不改它。它继续是你手写的文档，模型按现在的方式按索引 `read`。

之后要不要让它进上下文，只剩一种可能值得试：按 tracker / 仓库标签推送 1–2 篇文章的摘要加路径（不是全文、不进 bank）。等前两段跑起来、看到模型在启动后还缺什么再测，不先设计。

## 7. 交接（close-out）

控制面在工作会话里跑一个隐藏回合，固定提示，输出：

```json
{
  "thread": "CAS-4672 | new:<slug> | none",      // 必填；null 让主会话猜是它最难的任务（实验 E）
  "stands": "一段",
  "next": [{"text": "…", "run": "me|agent|notify|checker", "on": "pr 288 | pod-tag cas-report ci-4821 | null"}],
  "produced": ["branch:…", "commit:…", "pr:…", "file:~/workspaces/pct/PCT-122738/report.md"],
  "learned": [{"text": "…", "anchor": "cas-credit/src/x.ts@a1b2c3 | null"}],
  "user_said": [{"text": "以后 header 编码不用 encodeURIComponent，原因是 …", "kind": "correction|preference|instruction"}],
  "next_time": ["做 cas-report 的改动先看 report-worker 的 cron 表"],
  "open": ["等 Allen 回 EWS 权限"]
}
```

控制面机械地：存交接文件、追加 tracker `Log`、替换 `Status`、勾选 / 追加 `Progress`（该会话是线程最新的才替换）、快照部分不碰、写 memhana 记录（第二段上线后：`learned` + `next_time` 为助手，`user_said` 为用户）、把整份交接作为事件投给主会话。会话里显示交接卡，你可改，改了再写。`thread: none` 的会话不建线程；90 个无编号会话大多如此。

实验 B 的结论：模型用 `gemini-3.8-flash`（与 `gpt-6-luna` 同质量，快 43%，省 33% 输出）；`glm-5.3-flash` 这类把预算花在隐藏推理上的模型不能用。提示要给 `user_said` 的正反例（纠正 / 偏好 / 教导 算，任务陈述 / 确认 不算）、要求看到 PR 号就写 `on: pr N`、`open` 要列所有在等的人和事。30 天内没有一个会话发生过压缩，压缩前交接保留为钩子但不是重点。

## 8. Tracker：目录不动，只改谁写

`~/workspaces/<prefix>/<ID>.md`、`pct/<ID>/`、`_templates` 保留。dashboard 删除（§9）。一个文件两部分：

- **快照部分**（你看的，写一次不要求更新）：`summary`、`epic`、`tvo`、`figma`、`wiki_docs`、`local_docs`、`related_cases`、`tags`、`priority`，Overview、Context、Notes。交接永远不碰。
- **状态部分**（程序和交接的）：`status`（active | waiting | needs-me | done | dropped）、`links`、`deploy_target` / `sprint`、`sessions`、`updated`；正文 `## Status`（交接替换）、`## Progress`（就是现在的清单，交接勾选 / 追加，行上可带 `on:` 条件和 `run:` me / agent / notify / checker；`on:` 可以是短码 `pr 752` 或一句话条件，两种检查器都要认）、`## Log`（交接追加）。

"更新太重"的根源是 skill 要工作会话每步手改清单。改成只由交接写，工作会话和你都不用管。解析器由控制面实现（`dashboard/data.mjs` 的 frontmatter 解析和 `sprint.mjs` 的部署节奏逻辑搬进来后删原文件），不再有"每个值必须单行"这种为旧解析器服务的约束。

## 9. 展示：工作台

主会话不是通知渠道。工作台页面从 tracker 文件和检查器状态渲染，模型不在渲染回路里。它完全取代 `~/workspaces/dashboard/`（静态页、`serve.mjs`、`data.mjs`、`sprint.mjs`、`check-frontmatter.mjs`、`pct-status-sync.mjs`）：同一份数据不留两个前端。

- 现在：needs-me（一键派工 / 打开会话）、已备好（agent 只读结果）、运行中。
- 线程：按状态分组；waiting 的显示条件、上次检查时间、证据；临近冻结 / 部署日而 `Progress` 没走完的标出。
- 线程详情：Status、Progress、Log（每条链接会话）、产物、快照部分、按线程召回的一段记忆（生成的，不是文件）。
- 页面负责一切能从文件算出来的：板、部署倒计时（CAS 冻结 / 页面到期 / 部署，EAI 日期）、7 天没动的高亮、`needs-me` 队列、检查器条件的求值；主会话只被问判断题（归线程、答问、升级、写记忆）。实验 E 把两个模型的全部动作按"文件能算 / 要判断"分过，这条线清楚。
- 侧栏：会话按线程折组；主会话置顶。
- 通知：只有 needs-me 的检查器触发和主会话标的紧急。其余你打开页面看。

## 10. 检查器与输入

脚本，不用模型，现有 scheduler 每 10 分钟跑：`pr`（评论 / CI / merged）、`actions`、`pod-tag`、`jira-fixversion`、`confluence-page`、`date`、`file`、`manual`。输出 true / false + 一行证据，写回 `Progress` 那一行，再作为事件投主会话。每日 tick：控制面把超期 `manual`、7 天没动的线程、临近日期的清单作为一个事件推给主会话。以后：邮箱 / Teams / GitHub / Jira 轮询，按发件人 / 仓库 / @ 规则过滤后作为事件投主会话——和检查器同一条路，模型只在慢路径上。

## 11. 搜索工具

L6。pi 暴露的是具名工具 `grep` / `find` / `read`。扩展替换实现：有 SCIP 索引覆盖的文件走 `scipq grep`（ripgrep + 所在函数标注，定义优先），没有就原样 rg；`read` 有索引时附一行定义 / 引用脚注。模型调的名字不变。更大的杠杆是 §5 的召回带路径：拿到路径就 `read`，省掉一轮 `grep`。衡量：每会话 `grep` 次数、启动到首次 `edit` 的轮数，两周对比，没降就撤。

## 12. 底层：pi 留

瓶颈不在 loop。需要的 pi 都有：只追加的会话文件（交接卡、关联是 custom entry）、`before_agent_start` 注入、`context` 钩子重建上下文（§4.2 的基础）、`compaction_start` 钩子、扩展工具、steer / queue、scheduler 和 subagents（fork 已有）、多 provider。没有的（异步工具、空闲钩子）控制面自己做。换 Claude Agent SDK 绑死模型；换 Python 栈等于重做桌面壳。pi-agent-desktop 的服务端从"托管会话"变成控制面：空闲与压缩前交接、tracker 状态部分、memhana 写入、检查器、工作台、主会话的上下文策略。

## 14. 顺序

1. 控制面：空闲交接（`gemini-3.8-flash`，提示 v2）+ 交接卡 + 交接文件 + 写 tracker 状态部分 + 侧栏折组 + 工作台只读渲染（含部署节奏、近期过滤、最后活动日期）。工作台能看了就删 dashboard。
2. 工作会话启动推送：tracker + BM25 over 交接文件，6k。
3. 主会话：`context` 钩子的上下文策略（§4，板过滤）、工具、固定的检查器动作集、事件投递、一键派工；模型 flash，强制 `remember`。
4. 检查器：`pr` / `date` / `manual` 起步。
5. memhana 第二路：本地已跑通（`memhana-local/run.sh`）；接交接写入、`items` 紧凑渲染、仓库过滤；两周 A/B。
6. `grep` / `read` 后接 scipq；两周看指标。
7. kb 标签推送的小测，只在前面都跑起来、启动后仍缺东西时做。
