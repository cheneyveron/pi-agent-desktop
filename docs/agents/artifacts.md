# Artifacts and inline previews

## What renders where
- **Inline previews** (`components/HtmlPreviewBlock.tsx`): a fenced block in any MarkdownBody gets a preview when `htmlPreviewKind()` (`lib/html-preview.ts`) accepts it — a complete HTML document (`<!DOCTYPE html>` / `<html>` root), an SVG (`svg`, `xml`, or `html` fence with an `<svg>` root), or a self-contained React module in a `jsx` / `tsx` fence (`export default`, JSX, no relative / `@/` / `~/` imports, no `require`). Fragments stay source-only. React fences always start as source. HTML/SVG with active content (`<script>`, `on*=` handlers, `javascript:`) preview on their own only when this page watched them stream in (`streamedPreviews`, keyed by the first 256 chars, because the streaming bubble and the finished message are different components); from history they show source and a Preview button. Reason: in the macOS app a sandboxed frame runs in the window's process, so a looping page would freeze the app every time its conversation opened.
- **Artifacts** (`lib/artifacts.ts`): assistant text only (`MessageView`'s `TextBlock` passes `artifacts` to MarkdownBody; user and tool text never do). Syntax is LibreChat's container directive, `:::artifact{identifier="…" type="…" title="…"}` + an inner fence + `:::`, parsed by a line scanner rather than remark-directive, which would also turn chat text like `:name` into directives. Types: html, react, svg, mermaid, markdown, code (MIME spellings such as `application/vnd.ant.react` are accepted; a missing type is inferred from the inner fence). `encodeArtifactsForMarkdown()` rewrites each block into a `pi-artifact` fence whose first line is a JSON header, so react-markdown hands it to the `code` component, which renders `ArtifactCard`. The fence that ends an artifact is the one followed by `:::`; the first bare fence is only the fallback (streaming, or no `:::`), because models nest same-length fences inside Markdown artifacts. The scan for that fence stops at the next `:::artifact{` line. Once complete, `shouldInlineArtifact()` keeps small Mermaid/SVG/Markdown artifacts and quiet, small HTML in the message; React, code, large documents, and scripted or active SVG/HTML use the right-panel card because they need space or must not run from history automatically.
- **Versions**: every occurrence of an identifier in the loaded transcript is a version, in order (`collectArtifacts`). Only loaded messages count; history pages not yet fetched are not versions yet.

## Data flow
- `ChatWindow` calls `useArtifactPublisher(sessionId, messages, streamingMessage, send)`. It publishes the session's artifacts (including the one a stream is writing) to `lib/artifact-store.ts`, a module store read with `useSyncExternalStore`, so AppShell's panel and cards deep inside memoized MarkdownBody share state without prop threading. Unchanged entries keep identity; up to 20 sessions are cached. Nothing is persisted: artifact tabs vanish on reload and are reopened from cards.
- AppShell registers the opener (`setArtifactOpener`); a card click or an automatic open (a card that saw its block go from streaming to complete) adds or re-targets one tab per `artifact:<sessionId>:<identifier>`. Automatic opens are skipped on mobile. The card reads `useHasArtifactOpener()` reactively: it renders before AppShell's effect runs, and MarkdownBody is memoized, so a plain read could strand a card in its no-panel fallback (which shows the content inline).
- `ArtifactPanel` reads the store and renders `ArtifactView`, which reuses FileViewer's toolbar classes so an artifact tab reads like a file tab. It follows the newest version unless the user picked an older one.

## Artifacts page (cross-session)
- Sidebar row under Scheduled (`components/artifacts/ArtifactsSidebarRow.tsx`) opens `ArtifactsView` over the chat area. AppShell's `workspaceView` (`?view=scheduled` / `?view=artifacts`) holds at most one page; picking or starting a session closes it, a cold-start restore behind it does not (`pageOpenRef`).
- **It never reads the chat's store.** The store only has the loaded window of the open conversation's active branch, chats have no right panel (the opener ignores them), and switching sessions closes other sessions' tabs. So the page previews from the server: `GET /api/artifacts?q=` lists, `GET /api/artifacts/item?session=&identifier=` returns every version's content.
- `lib/artifact-index.ts` parses session files with `splitArtifacts` (assistant text only, like the chat), cached on `globalThis` by path + size/mtime. A file whose bytes lack `:::artifact`, a file-tool name and every deliverable extension is not parsed (with the extensions most files qualify, so persistence matters more), and a cold pass still reads every session file (≈440 MB / 1.9 s on a real 437-session home), so the cache is also written to `~/.pi/agent/pi-web/artifact-index.json` (debounced, atomic, versioned by `PERSIST_VERSION`; a bad file is ignored) and seeded from it once per process: after a restart only files whose fingerprint moved are read (first request ≈0.2 s). Paths are pruned only after a pass that was not aborted. Tests keep persistence off unless they pass a path to `resetArtifactIndexForTests`. Session paths come only from `listAllSessions({ allowStale: true })`.
- Versions are every occurrence in file order across all branches; `onActiveBranch` follows the SDK's leaf (the last entry in the file). Only active-branch versions get "Show in conversation", which reuses the search jump (`handleOpenSession(sessionId, entryId)` → `searchTarget`, loading older pages until the entry appears).
- A fork's artifacts are hidden when every version's hash is also in its source session (it is a copy). Subagent sessions are skipped; scheduled runs are listed and tagged.
- Search is literal and case-insensitive over identifier, titles, then content (newest version first, snippet only for content hits). Type and project/Chats filters run client-side over the newest 500 (`components/artifacts/artifacts-helpers.ts`).
- The preview passes `holdActiveContent`: React and scripted HTML/SVG start in Source until the user picks Preview, the same rule as history. "Ask to fix" is not offered there. The list reloads on window focus (at most every 10 s) and when a running session finishes. The last lists per search are kept in a module cache, so reopening the page paints the previous list at once and refreshes in the background; an unchanged answer keeps the list's identity, and only a changed search dims the list (`is-loading`).
- **Thumbnails** (`components/artifacts/ArtifactThumbnail.tsx`) show each row's newest version (`/api/artifacts/item?latest=1`). **Never a live frame**: one `iframe` per row (the earlier design) made dragging the scrollbar drop frames, because each mount is a whole document to parse and lay out. Every thumbnail is an `<img>` or a text excerpt: SVG and Mermaid as images; HTML laid out at 800x600 inside an SVG `<foreignObject>` (`pageImageSvg`) after scripts, frames, plugins, `link` and `base` are stripped — as an image it can run nothing and load nothing; Markdown/code an excerpt; React keeps its icon. Images are rasterised once to a 128x96 PNG; WebKit refuses to export a canvas that drew a foreignObject, so there the SVG itself is used. Work runs through one queue, one job at a time, only after the list has not scrolled for 150 ms, newest request first, skipping rows that left the viewport's neighbourhood; results are cached in memory and read synchronously, so a cached thumbnail paints with its row (only fresh ones fade in). One shared `IntersectionObserver` per list watches the rows (`li`), which use `content-visibility: auto`. Measured in headless Chromium on 400 rows, fast sweeps went from p95 33 ms / max 83 ms with 19 dropped frames to 16.8 ms with none. `ArtifactThumbnail.test.mjs` pins no `iframe`, the stripped elements and the scroll-idle wait.
- **Continue in new chat** forks the source session at the shown version's entry (`fork_branch`, which also works for versions on other branches) and sends a prompt naming the artifact, title and version plus the user's request, through the same `pendingQuotePrompt` → `initialPrompt` path as "Ask in new chat". AppShell opens the fork from its own `/api/sessions/[id]` info, since the source is usually not the session on screen.

## Files the agent wrote (Artifacts page)
- The page lists two kinds (`OutputSummary`): `:::artifact` blocks, and **files** written or edited by the `write` / `edit` tools. Only calls whose `toolResult` exists and is not `isError` count (failed and interrupted calls are dropped).
- **Files a command made** (bash, a python heredoc, `cp`) are found by what the conversation *said*, never by parsing the command: the index records deliverable paths (`isDeliverablePath`: html, md, pdf, office, csv, images, media) named in user text and in assistant text blocks (`IndexedMention`; not tool results, not thinking). Code spans, link targets and bare runs are extracted; a run that swallowed CJK prose resolves to nothing and drops out. A file with no write/edit is listed only when a reply named it, it is still on disk, and its birth time (`mtime` where there is none) falls between the naming session's `created` and the reply, with 5 min slack: a reply explaining an existing document does not list it.
- **Outputs vs process files** (`lib/file-output-role.ts`, `classifyFileOutput`). The default view (empty type) shows artifacts and output files; process files only under `files:process` or `all`, with a "N process files not shown" line under the list. An output is a deliverable path that the user named (`requested`), a reply named (`mentioned`), or a `write` created outside any git work tree (`created`). Project work is not an output: a file under a dot folder (measured from the session cwd, else home, so a worktree under `.claude/worktrees/` still counts) or an existing repository file that was only edited, unless the user named it. Repository files a `write` created count only when a reply named them. Non-deliverables (code, config, scripts, data) are always process files.
- **Hidden entirely** (`isHiddenOutputPath`): credential names (`auth.json`, `.env*`, keys) and anything under `node_modules` or `.git`. A real history has an `edit` of `auth.json` holding an API key; its preview would show it, so it is not even a process file, and overrides cannot bring it back.
- **Manual overrides** win over the rules: `PUT /api/artifacts/file { path, role: "output" | "process" | null }`, only for a path the page lists, stored by absolute path in `~/.pi/agent/pi-web/artifact-file-roles.json` (`lib/artifact-file-roles.ts`). The row tag then reads "Added by you"; null returns to the rules.
- **Favorites**: the star in the detail pane's source row toggles `PUT /api/artifacts/favorite` (`{ kind: "file", path }` or `{ kind: "artifact", sessionId, identifier }` plus `favorite`), stored as keys in `~/.pi/agent/pi-web/artifact-favorites.json` (`lib/artifact-favorites.ts`; files by path, artifacts by session + identifier). `listArtifacts` sets `favorite` on each row; the page updates its remembered lists at once and the next load confirms. The star button after the project picker filters to favorites; with the default type that includes starred process files.
- **List width**: the handle between list and preview (`useResizablePanel`, `--artifacts-list-width`, stored as `pi-artifacts-list-width`) drags between 300 and 640 px, and never past the page width minus 360 px for the preview; double-click or Enter resets to 360. Hidden on narrow screens, where list and preview take turns.
- **Row right-click** (desktop only, `showMenu` from `hooks/useFileContextMenu.ts`, so native popup or the in-app fallback): "Open the conversation that produced it" scrolls to `conversation` (the newest producing entry on an active branch; disabled without one), and for files "Open with default app" (`open_path`) and the platform's reveal item. In a browser the browser menu stays.
- **The index keeps no file contents** (`IndexedFileOp`: path as written, tool, tool-call id, entry, time, branch; `IndexedMention`: path, who, entry, time, branch). It is persisted, and written files can hold secrets (a real history has an `edit` of `auth.json` with an API key); a test asserts written content never reaches `artifact-index.json`.
- Files are one row per absolute path (`resolveFileOpPath`: `~` → `userHome()`, relative → session cwd), merged across every session that touched them; calls are deduped by tool-call id, so a fork's copies count once. The row's session is the latest call's. `displayPath` is project-relative, else `~/…`, else absolute. Files gone from disk (deleted, or their folder moved) are left out of the list: they cannot be opened. `missing` stays for a file that disappears while its detail is open, where the last `write` comes back from the transcript. Search matches the path only.
- The preview is `FileViewer` with `sourceSessionId` = the latest call's session, so `/api/files` authorizes the path through its session-reference rule; nothing here widens the allow-list. `GET /api/artifacts/file?path=` lists the calls (for a file no call recorded, the replies that named it, as `tool: "mention"`); `?session=&toolCallId=` reads one `write`'s content back from the transcript, shown (via `ArtifactView`, held like other history) when the file is gone from disk.
- Type filter values beyond artifact types: `artifacts`, `files` (output files), `files:process`, `all` (outputs and process files). An output row carries its strongest reason as a tag. File thumbnails go through the same queue: images (and SVG, which `/api/files` serves as an image) are rasterised from `/api/files?type=read`, HTML/Markdown/code reuse the artifact renderers on the text, anything else shows its file icon.

## Sandbox (do not weaken)
- Every preview is an `srcDoc` iframe with `HTML_PREVIEW_SANDBOX` = `allow-scripts allow-forms allow-popups allow-popups-to-escape-sandbox`, never `allow-same-origin` (opaque origin: no app cookies, storage or `/api/*`). Tests pin the absence of `allow-same-origin`.
- The bootstrap injected first into every document (`bootstrapScript`) replaces localStorage/sessionStorage with in-memory stand-ins (opaque origins throw on access), reports size, reports uncaught errors / rejections / failed resource loads (max 5, deduped, 500 chars), and handles links: in a browser it sets `target=_blank` so `allow-popups-to-escape-sandbox` opens a normal tab; in the desktop app it posts `pi-html-preview:open` and `useHtmlPreviewFrameMessages` opens http(s) URLs with `openExternal` — only while that frame has focus (the user clicked in it) and at most once a second. Messages are matched by `event.source`.
- **Desktop shell**: WebKit asks the navigation delegate about sub-frame loads as well, and `build_window`'s `on_navigation` cancels anything not on the app origin. `is_inline_frame_document()` (`src-tauri/src/lib.rs`) lets `about:srcdoc` / `about:blank` through; without it every srcdoc preview (and FileViewer's "Run scripts") is blank on macOS.
- Theme: a page that sets no colours (`htmlPreviewFollowsTheme`: no `background`/`color` declarations, `bgcolor`, stylesheet links or Tailwind CDN) gets the app's canvas and text colours injected; anything styled keeps a white canvas, and SVG and React always do.

## React runtime
- React 19 + ReactDOM, the JSX/TSX compiler (Sucrase) and Tailwind's browser build ship with the app in `public/preview-runtime/` (≈660 KiB, committed). `scripts/build-preview-runtime.mjs` (`npm run preview-runtime`) builds them from the pinned devDependencies `sucrase`, `@tailwindcss/browser` and `esbuild` plus the app's own `react` / `react-dom`; `scripts/preview-runtime.test.mjs` fails when package-lock.json moved without regenerating, and also executes the bundles and compiles JSX with them.
- **They are inlined, never loaded by URL.** Chromium refuses every request from a sandboxed (opaque-origin) frame to localhost/127.0.0.1, while external hosts still load — verified in the desktop app's Chromium 152. So the page fetches the files itself (`lib/preview-runtime.ts`, same origin, once per page, revalidated via `Cache-Control: max-age=0, must-revalidate` in next.config.ts) and `buildReactDocument` inlines them as classic scripts (`</script` escaped to `<\/script`, which only occurs in strings, regexes and comments). Do not "simplify" this back to `<script src>` or module URLs pointing at the app.
- The import map points `react`, `react/jsx-runtime` (and `jsx-dev-runtime`), `react-dom`, `react-dom/client` at `data:` modules that re-export `globalThis.__piPreviewRuntime.<Global>`; `manifest.json` lists the export names. Every other bare specifier maps to `https://esm.sh/<spec>?external=react,react-dom`, so packages bind to this same React (two Reacts break hooks). Those packages need the network; a component that imports only React works offline.
- The compiled component is imported from a blob URL with a `data:` URL fallback. The component is `default` ?? `App` ?? the first exported function. React previews wait for the runtime (placeholder text, then the frame); a failed load shows in the error bar.

## Fix flow and prompt
- The error bar's "Ask to fix" sends a localized request (`preview.fixPromptArtifact` / `preview.fixPromptHtml`, errors fenced by `formatPreviewErrors`) through ChatWindow's `handleSend`, which already merges the text into the composer while a run is busy. While an earlier message is being edited it goes to the composer instead, because sending would replace that branch. It is offered only for the session that registered the handler (`requestArtifactFix`).
- `lib/artifact-guide-extension.ts` adds an `<artifacts>` section to `systemPromptOptions.sections` on `before_agent_start` for normal sessions (not chat-only or subagents, whose prompts are exact). The switch in Settings › General › Chat is stored in `~/.pi/agent/pi-web/settings.json` (`artifactsPrompt`, default on, unreadable file = on), not pi's settings.json, which other hosts read; it is re-read on every run. Rendering does not depend on it.
